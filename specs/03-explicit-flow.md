# ТЗ: доработка `main` — явные вызовы внутри, события только на границе

> Версия 1 от 06.10.2026. Исполнитель — GigaCode (агент), ревью — архитектор и тимлид.
> База — `main` после выполнения `specs/02-main-alignment.md`: модули `domain.ts` с `ctx.handle` / `ctx.on` / `ctx.onCommand`, доменные факты, факты `command.*` на шине, `defineCommand` и `useCommand`, канал команд с политиками, шина `Bus`, готовность к RxJS, требования к качеству кода и `npm run quality`.
> Порядок работы: агент получает весь файл и номер этапа из раздела 6. Следующий этап — только после прохождения проверок предыдущего.

## 0. Цель

Упростить отладку и чтение кода. Сейчас связи между доменами идут через события: доменные факты, `ctx.on` в фичах, `ctx.onCommand`, причинная цепочка `cause`, карта `routes:map`. Чтобы понять, почему что-то произошло, нужно восстанавливать цепочку по ленте DevTools.

Целевая модель — **явно внутри, события только на границе**. Домены и их границы остаются; меняется способ, которым они связаны:
- факты инфраструктуры (транспорт, платформа, служебная сессия) переводятся в вызовы команд **в одном файле** `app/engine/inbound.ts`;
- внутри одного действия пользователя — **прямые вызовы** в сценарии;
- «показать, если…» — **производное состояние** (селекторы), а не реакции с таймерами;
- наружу — публичные события для плагинов, как сейчас.

Результат: цепочку показывает стектрейс, причину — состояние в DevTools, ответ на вопрос «что происходит, когда приходит X» — один экран `inbound.ts`.

## 1. Что не меняется

- **Домены и раскладка по ним.** Каждый домен (`message`, `thread`, `session`, `composer`, `history`, `file`, `config`) по-прежнему владеет своим срезом, мутаторами, селекторами, командами и сценариями; сущность — в `entities/<домен>`, пользовательские действия и процессы — в `features/<домен>/<действие>` (группы по 2.6). Регистрация команд домена — в его `domain.ts` (`ctx.handle`). Убирается только событийная связь между доменами: подписки слайсов на шину, доменные факты, `ctx.onCommand`.
- Объекты команд `defineCommand`, вызов из UI через `useCommand`, вызов из сценариев и `inbound.ts` через `dispatch(command(payload))`; описатели политик `takeEvery` / `takeLatest` / `takeLeading` / `takeQueued` / `silent`; канал команд, его реестр, политики, `signal`, исходы `superseded` / `deduplicated`.
- Готовность к RxJS (`02-main-alignment.md`, разд. 2.1): интерфейс `Bus`, нормализация результата в канале, отмена через `abort()`, контрактные наборы `describeBusContract` и `describeCommandChannelContract` — проходят после изменений; шаги, вызываемые напрямую, — `async`.
- Порты, адаптеры, каналы транспорта и платформы, фейковый бэкенд, машина состояний сессии, публичный API (`ChatProvider`, `createChat`, `mount`, имена и форма хуков, компоненты), публичные события и плагины.
- Тесты `tests/contracts`, `tests/e2e`, `tests/fuzz`, `tests/memory` — проходят без изменения проверок.
- Требования к качеству кода и пороги `npm run quality` из `02-main-alignment.md`, разд. 7 — действуют; конфиг уже в репозитории.

## 2. Целевая модель

### 2.1. Граница: `app/engine/inbound.ts`

Единственное место, где факты инфраструктуры превращаются в команды.

```ts
// app/engine/inbound.ts
export type InboundEvent = { [K in keyof InternalEventMap]: { type: K } & InternalEventMap[K] }[keyof InternalEventMap];

export function handleInbound(e: InboundEvent, dispatch: Dispatch): void {
  switch (e.type) {
    case 'transport.message.received':
      return dispatch(receiveMessageCommand({ message: e.message }));
    case 'transport.message.acked':
      return dispatch(ackMessageCommand({ ack: e.ack }));
    case 'transport.connection.changed':
      dispatch(connectionChangedCommand({ state: e.state }));
      if (e.state === 'connected') dispatch(flushOutboxCommand());
      return;
    case 'transport.session.invalidated':
      return dispatch(restartCommand({ reason: e.reason }));
    case 'transport.session.restarted':
      return dispatch(hostRestartedCommand({ epoch: e.epoch }));
    case 'platform.app.resumed':
      return dispatch(resumedCommand());
    case 'platform.app.paused':
    case 'session.status.changed':
      return;                                         // явно: реакции нет
    default:
      return assertNever(e);
  }
}
```

- `createEngine` подписывает `handleInbound` на шину через `bus.onAny` (или по ключам `InternalEventMap`) — **одна подписка на инстанс**; `cause` у вызовов — id факта.
- Каждый ключ `InternalEventMap` обработан явно: пропуск — ошибка компиляции (`assertNever`), «нет реакции» — пустая ветка с комментарием.
- В `inbound.ts` нет условий сложнее одного `if` по полю факта, нет состояния и таймеров. Если решение сложнее — это сценарий, который вызывается отсюда.
- `inbound.ts` импортирует объекты команд из слайсов — это допустимо: `app` стоит выше всех слоёв.

### 2.2. Внутри одного действия — прямые вызовы

Если реакция — часть того же действия пользователя, она пишется в сценарии этого действия прямым вызовом действия среза или функции шага.

```ts
// features/message/send/model/send-message.ts
export async function sendMessage(d: Pick<Deps, 'store' | 'transport' | 'ids' | 'timers' | 'signal' | 'publicEvents'>, p: SendPayload): Promise<SendResult> {
  d.store.getState().composerActions.clear(p.threadId);     // было: фича composer-clear на onCommand('message/send', 'started')
  // …
}
```

- Последовательность шагов процесса — `await` функции шага (как в базе).
- Независимая работа в другом домене — `d.dispatch(command(payload))`.
- Правило ревью: сценарий содержит только то, что относится к его действию; «раз уж мы здесь» — нарушение.

### 2.3. «Показать, если…» — производное состояние

Условия, зависящие от нескольких фактов и времени, выражаются селектором над стором, а не подписками и таймерами.

- В сторе хранятся **входные данные** с отметками времени: `session.disconnectedSince: number | null`, у сообщения — `failedAt`, `sentAt`; срез `clock` (уже есть для относительного времени) тикает раз в секунду, пока на него кто-то подписан.
- Решение — **чистая функция** от этих данных и `now`: `selectShowConnectionBanner(s) = s.session.disconnectedSince !== null && s.clock.now - s.session.disconnectedSince >= CONNECTION_BANNER_DELAY_MS`.
- Компонент подписывается на селектор; на `clock` подписаны только компоненты, которым нужно время.
- Тесты — таблицами: входные данные + `now` → ожидаемый результат.

### 2.4. Что удаляется

- `ctx.on` в модулях сущностей (переезжает в `inbound.ts`) и в модулях фич (классифицируется по разделу 3).
- `ctx.onCommand`, `serviceFacts`, разделение `EntityContext` / `FeatureContext`: остаётся один `ModuleContext` с методом `handle`. Файл `domain.ts` слайса содержит только регистрацию команд.
- Доменные факты: `DomainEventMap`, `d.events`, их публикация в сценариях. Публичные события (`d.publicEvents`, `PublicEventMap`) остаются.
- Факты `command.started` / `command.done` / `command.failed` на шине. Канал команд сообщает о вызовах только через хуки инспектора (`onCommandStart`, `onCommandEnd`) для DevTools; на шине их нет.
- Скрипт `routes:map` — его заменяет `inbound.ts`.
- Защита от циклов через глубину `cause`: циклов через события больше нет. `cause` остаётся как метаданные вызова для ленты DevTools (`ui`, id факта, id родительской команды); проверка повторов и глубины удаляется.
- Таймеры в фичах, которые нужны только для «показать через N секунд», — заменяются производным состоянием.

### 2.5. Хуки — только клей

- Хук выбирает данные селекторами и возвращает стабильные функции, вызывающие `useCommand(command)`.
- В хуках `entities` и `features` запрещены `useEffect` (кроме работы с DOM в `ui/`), прямой доступ к транспорту, платформе и шине — правило линтера.
- Процессы (приём, outbox, рестарт) не зависят от того, какие компоненты смонтированы: они запускаются из `inbound.ts` и сценариев.

### 2.6. Группы слайсов по доменам (FSD)

Слайсы `features` группируются по доменам — это штатная возможность FSD («группы слайсов»): в папке группы нет общего кода, слайсы внутри изолированы друг от друга.

```
features/
├─ message/   send/  retry/  load-older/
├─ session/   lifecycle/  recovery/
├─ thread/    open/
├─ outbox/    flush/
└─ banner/    connection/  delivery/
```

- Фича, затрагивающая несколько доменов, лежит в группе домена, с действием пользователя которого она связана (`recovery` — `session`).
- Steiger: проверить, что используемая версия понимает группы; если нет — правила групп держит `eslint-plugin-boundaries`, а Steiger для групп настраивается или отключается (описать в отчёте).

## 3. Классификация существующих подписок (результат этапа 1)

Файл `reports/explicit-flow-inventory.md`. Для каждой подписки из вывода `routes:map` и каждого `ctx.onCommand` — одна из категорий и целевое место:

1. **Граница** — факт инфраструктуры → команда: переносится в `inbound.ts`.
2. **То же действие пользователя** — прямой вызов в сценарии этого действия (пример: очистка черновика при отправке).
3. **Производное состояние** — условие от нескольких фактов и времени: входные данные в срез, селектор, компонент (пример: баннеры соединения и доставки).
4. **Наблюдаемость** — реакция ради логов, аналитики, уведомлений хоста: плагин на публичных событиях; если данных не хватает — расширить `PublicEventMap`.
5. **Независимый процесс** — реакция запускает отдельную работу в другом домене и не является частью действия пользователя: вызов команды из сценария-источника через `d.dispatch(command(payload))` или из `inbound.ts`, если источник — инфраструктура.

Подписка, которую нельзя отнести ни к одной категории, — выносится на обсуждение с архитектором до переноса.

## 4. Контрольная фича после переделки

- **Баннер соединения:** `session.disconnectedSince` выставляется сценарием `session/connectionChanged` (`null` при `connected`); `selectShowConnectionBanner` по 2.3; плашка — компонент на селекторе. Сущность `banner` со срезом `visible` и команды `banner/show` / `banner/hide` удаляются, если не используются ничем другим.
- **Баннер доставки:** `selectShowDeliveryBanner(s) = число сообщений с failedAt за последние 60 с ≥ 3 и после последнего failedAt нет sentAt и не было session.restoredAt`.
- **Тесты** — таблицами по селекторам с `now`; поведенческие тесты раздела «Контрольная фича» базы (короткий обрыв, длинный обрыв, восстановление, 2 и 3 неудачи, окно 61 с, `dispose` во время ожидания) проходят с тем же смыслом.

## 7. Чего не делать

- Не возвращать подписки на шину в слайсы — подписка на факты инфраструктуры только в `inbound.ts`, на публичные события — только в плагинах.
- Не заменять производное состояние реакциями с таймерами; не хранить в сторе «показан ли баннер», если это вычисляется из входных данных.
- Не переносить процессы в хуки и `useEffect`.
- Не класть в сценарий вызовы, не относящиеся к его действию.
- Не менять объекты команд, канал команд, политики, порты, транспорт, публичный API.
- Не трогать `specs/01-demo-skeleton.md` и `specs/02-main-alignment.md`: этот документ — дополнение к ним.
