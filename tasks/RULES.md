# Общие правила (читать перед любой задачей)

Цель: рабочее MVP чата, минимум кода, чистая архитектура, понятно с первого прочтения.
Проекты — 4 независимых, каждый в своей git-ветке и своём worktree. Они сравниваются по архитектуре, поэтому **код модели пишется идиоматично для своей библиотеки**, а всё остальное одинаково.

## Жёсткие ограничения

- Файл ≤ 80 строк. Функция ≤ 25 строк. Если больше — раздели.
- Без `any`, `as unknown as`, `!`, `@ts-ignore`. `as const` можно.
- Именованные экспорты, без `default`.
- Без persist (`localStorage`, `sessionStorage`, IndexedDB, cookies).
- Не добавлять зависимости сверх указанных в задаче. Нельзя: lodash, axios, moment, xstate, redux.
- Не менять `src/shared/contract.ts`, `src/shared/backend.ts`, `src/shared/ui/*`, `src/shared/chat.contract.ts` (в ветках; правит только база).
- Нет e2e, нет Playwright, нет ESLint-настроек, нет DevTools, нет логгеров, нет «на вырост».
- Идентификаторы по-английски, комментарии по-русски и только там, где неочевидно «почему».
- Тесты: только `src/model/chat.test.ts` из 3 строк (вызов `describeChat`). Новых тестов не писать.
- Не придумывать требований. Не хватает — сделай проще и запиши одну строку в `NOTES.md`.

## Раскладка модели (FSD-lite, одинаковая во всех проектах)

```
src/model/
  entities/message/       хранение и слияние сообщений
  entities/connection/    состояние соединения
  features/send/          отправка, повтор, таймаут ack
  features/receive/       входящие из backend.on
  features/outbox/        дослать pending при connected
  features/load-older/    подгрузка истории
  features/connection-banner/   баннер: reconnecting ≥ 3 с
  create-chat.ts          собирает всё, возвращает Chat из contract.ts
  chat.test.ts
```
Слои импортируют только вниз: `create-chat` → `features` → `entities`. Сущности друг друга не знают. Фичи могут использовать несколько сущностей.

## Поведение (общее для всех проектов)

1. `start()`: подписка на `backend.on`, `backend.connect()`, загрузка первой страницы истории (30 сообщений, хранить от старых к новым).
2. Входящее `message`: добавить; если есть `clientId` и такое сообщение у нас уже есть — заменить им (статус `sent`); если `id` уже есть — игнорировать (дубликаты).
3. `send(text)`: сразу показать сообщение со статусом `pending` (свой `clientId`, `author: 'me'`). Вызвать `backend.send`. Успех — `sent`, подставить серверный `id`. Ошибка `offline` — остаётся `pending` (ждёт outbox). Нет ack за 10 с — `failed`.
4. `retry(clientId)`: только для `failed` → `pending` и снова отправить с тем же `clientId`.
5. Outbox: при переходе в `connected` отправить все `pending` с их `clientId`.
6. `loadOlder()`: если `hasOlder` и не идёт загрузка — загрузить страницу до самого старого `id`, добавить в начало. Повторный вызов во время загрузки игнорируется.
7. Баннер: `showConnectionBanner = true`, если соединение `reconnecting` непрерывно 3 с; любой `connected` скрывает сразу; короткий обрыв баннер не показывает.
8. `dispose()`: отписаться от backend, остановить таймеры. После dispose никаких обновлений состояния.
9. Таймеры (10 с ack, 3 с баннер) — только через `setTimeout`, чтобы работали `vi.useFakeTimers()`.
10. Порядок в ленте: `createdAt`, при равенстве `id`.

## Как сдавать

В конце работы в своём worktree: `npm run typecheck && npm test` зелёные, `npm run dev` стартует (не запускать, только `npx vite build` для проверки). Коммит одним сообщением `feat: <что>`. Не пушить. В ответ — 5 строк: что сделано, число строк в `src/model` (`find src/model -name '*.ts' | xargs wc -l`), что отклонил от ТЗ.
